# 发布-订阅模式 vs MVC 通知机制 精炼笔记

---
> [C语言-发布订阅模式详解与实践](https://blog.csdn.net/Set_Mode/article/details/108106324)

---

## 1. 模式本质
- **发布-订阅(Pub/Sub)**：通过独立的**消息代理/事件通道**解耦，发布者与订阅者互不知晓。  
- **MVC 通知机制**：基于**观察者模式(Observer)**，Model(主题) 直接维护 View(观察者) 列表并通知。

## 2. 结构差异
- **Pub/Sub**：`发布者 → 消息代理(Topic) → 订阅者` （三方协作，代理是核心）
- **MVC**：`Model(持有View列表)` → 直接调用 `View.update()` （无中介，直接依赖）

## 3. 数据传递方式（最关键区别）
- **发布-订阅**：消息**自带完整数据（推送式）**。订阅者收到后可直接消费，无需回查源头。
- **MVC(拉模型)**：通知**仅是一个“状态变更信号”**，不携带数据。View 收到通知后**主动向 Model 拉取**最新数据，再按需更新。

## 4. 耦合与依赖
| 模式 | 耦合特点 |
|------|----------|
| Pub/Sub | 极低：发布者与订阅者互相无依赖，只依赖消息代理与 Topic 名称 |
| MVC   | 松耦合但接口依赖：Model 依赖抽象 Observer 接口，View 依赖 Model 具体数据接口 |

## 5. 通知后的处理方式
- **Pub/Sub**：订阅者直接处理消息中携带的数据，各行其是。
- **MVC**：View 收到通知 → 反问 Model 拿到数据 → 各自处理界面更新（逻辑在 View 内）。

## 6. 典型应用与通信边界
- **Pub/Sub**：跨进程、分布式、微服务、事件驱动架构（Redis, RabbitMQ, Kafka）。
- **MVC**：单应用内 UI 与业务数据同步（传统 MVC 框架、桌面/前端组件）。

## 7. 核心对比速览表
| 对比点 | 发布-订阅模式 | MVC (观察者模式) |
|--------|--------------|-----------------|
| 中间人 | 必须有消息代理 | 无，Subject 直接通知 |
| 通知携数据 | 通常携带完整事件数据 | 通常不携带（仅有信号） |
| 数据流向 | 发布者→代理→订阅者(一次到位) | Model自更新 → 通知View → View拉取 |
| 互相感知 | 完全不知 | Subject 明确知道 Observer 列表 |
| 控制流程 | 异步为主 | 同步或异步，Model 主动驱动 |

## 8. 极简记忆
- **发布-订阅** = **快递送货上门，包裹里直接有货**（消息带数据）。  
- **MVC通知** = **短信提醒“货物有变”，自己去仓库(Model)查看并取货**。
